Globals

Every Luau script in a Ruzit project starts with a small set of runtime-injected globals on top of the standard Lua library. import, require, __dirname, load, and print, covered below.

Per-script env. Each loaded module runs inside its own environment table that inherits from _G via a metatable. The globals listed here are installed on that env per-script, which is why __dirname reports the directory of the script that references it, not some single global value.

import

import(name) → <library API>

Library accessor. Pass any name from the API Reference , "Renderable", "Window", "Steam", etc., and you get a typed handle to that subsystem. 

local Window = import("Window")
local Renderable = import("Renderable")
local Vector = import("Primitives").Vector

Unknown names throw a "unknown library 'X'" error at runtime, with a "did you mean?" hint that scans for the closest valid name. The Luau LSP follows the return type through every import(...) call, so hover docs and autocomplete work automatically once types.d.luau is in your project.

Available libraries

Twenty-one as of v3.2: Actor, Asset, Gamepad, GPU, GUI, IO, Keyboard, Managed, Mouse, Net, Primitives, Process, Register, Renderable, Serde, SFX, Signal, Steam, Voice, VR, Window. Each has its own page in the API Reference sidebar.

require

require(name) → any

Load a sibling Luau module from inside the project bundle. The first call evaluates the module; subsequent calls return the cached return value, so a module is initialised at most once.

Path forms

"./helper" Caller-relative. Resolves to a sibling file.
"../shared/util" Parent-relative.
"subdir/file" Relative-without-./ also works.
"@PkgId/path/inner" Cross-package. Reads from another loaded .managed package.
"@self/lib/util" Same package as the caller, root-relative regardless of the caller's depth.

Resolution mode is controlled by "File Type" in build.toml: in "Relative" mode (the default) every path is caller-relative; in "Global" mode bare paths are resolved from the project root, but ./-prefixed and @PkgId/ paths keep their explicit semantics.

The .luau / .lua extension is appended automatically, pass the bare module name. Folder-style modules with an init.luau resolve when you require the folder name. 

local util = require("./util")
local phys = require("@PhysicsDLC/init")
local root = require("@self/lib/Math")

__dirname

__dirname string read-only

Absolute path of the calling script's directory. Each script sees its own value, not a single global, so relative paths can be built without coordinating with the rest of the project. 

local data = require(__dirname .. "/data/levels")
local img  = Asset.ImportAsset("Image", __dirname .. "/portrait.png")

Inside a packaged .managed bundle, __dirname is the script's vfs key, still works with require but isn't a real disk path. For raw filesystem access from inside a bundled script use Asset.ImportAsset instead of IO.read.

load

load(path) → any

Sibling to require that takes a raw filesystem path instead of a vfs key. Useful for loading mods, user-content scripts, or anything that lives outside the project's bundled tree. Returns whatever the loaded chunk returns, or true for bare side-effect modules (matching require's convention).

Path forms

"C:/mods/init.luau" Absolute Windows path.
"/usr/local/share/ruzit/x.luau" Absolute Unix path.
"./helper" Relative to the calling script's __dirname.
"./helper.luau" Same with explicit extension.

If no extension is provided the loader probes .luau then .lua. Errors are explicit: "load: file not found 'X' (resolved to '/abs/X')".

Loaded modules' environment

Every loaded module gets the full runtime env , require, import, __dirname, load, print, with file resolution rooted at the loaded file's own directory. So a script loaded from C:/mods/foo.luau can do require("./bar") and get C:/mods/bar.luau; nested load calls work the same way. 

-- main.luau
local mod = load("C:/mods/init.luau")
mod.run()

-- C:/mods/init.luau
local util = require("./util")        -- C:/mods/util.luau
local Window = import("Window")       -- engine library
return { run = function() Window.Open() end }
Don't confuse with Lua's built-in load. Standard Lua has a load(string) function for evaluating source strings. Ruzit shadows it on the script env with this file-loading version, load("print('hi')") won't work, you'd need to write the source to a file first or use Asset.FromString("File", ...) for in-memory text.

print

print(...)

Tab-separated, newline-terminated stdout. Coerces every argument to a string via Lua's standard tostring rules, falling back to {...}-style debug formatting for non-coercible values (function references, etc.). 

print("player", player.name, "hp", player.hp)
Console attach. A windowed launcher built with exe-windowed = true in build.toml has no console by default, so print output goes nowhere. Pass --console on the command line to attach (or allocate) a console window for debugging. See CLI.
