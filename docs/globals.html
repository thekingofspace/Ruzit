Globals

Every Luau script in a Ruzit project starts with a small set of runtime-injected globals on top of the standard Lua library. import, require, __dirname, load, and print, covered below.

Per-script env. Each loaded module runs inside its own environment table that inherits from _G via a metatable. The globals listed here are installed on that env per-script, which is why __dirname reports the directory of the script that references it, not some single global value.

import

import(name) → <library API>

Library accessor. Pass any name from the API Reference, "Renderable", "Window", "Steam", etc., and you get a typed handle to that subsystem. 

local Window = import("Window")
local Renderable = import("Renderable")
local Vector = import("Primitives").Vector

Unknown names throw a "unknown library 'X'" error at runtime, with a "did you mean?" hint that scans for the closest valid name. The Luau LSP follows the return type through every import(...) call, so hover docs and autocomplete work automatically once types.d.luau is in your project.

Available libraries

Twenty-four as of v3.8: Actor, Asset, Debug, DynMesh, Gamepad, GPU, GUI, IO, Keyboard, Managed, Mouse, Net, Primitives, Process, Register, Renderable, Serde, SFX, Signal, Steam, Video, Voice, VR, Window. Each has its own page in the API Reference sidebar.

require

require(name) → any

Load a Luau module from the project bundle (or a loaded DLC / .managed package). The first call evaluates the module; subsequent calls return the cached return value, so a module is initialised at most once. The .luau / .lua extension is appended automatically — pass the bare module name.

Path forms

FormResolves to
"./helper" Sibling of the caller (when caller's package is in Relative mode), or caller's package root + helper (when caller's package is in Global mode). See File Type.
"../shared/util" Parent-relative. Only meaningful in Relative mode.
"subdir/file" Same as ./subdir/file, the leading ./ is optional.
"@self/lib/util" Caller's own package, root-relative (or init-anchored, see @self).
"@Game/lib/util" Always the base game package, regardless of where the caller lives. The escape hatch a DLC uses to reach back into the game.
"@PkgId/path/inner" Specific named package. Use the package's ID from its ManagedInfo.toml. Equivalent to require(Managed.GetPackage("PkgId").Origin) when pointing at the package entry.

File Type — Relative vs Global

Each package picks a resolution mode in its build.toml / ManagedInfo.toml:

  • "File Type" = "Relative" (default): bare and ./-prefixed paths resolve relative to the calling file's directory. So if test/re.luau does require("./fah"), you get test/fah.luau.
  • "File Type" = "Global": bare and ./-prefixed paths resolve from the caller's package root — the game's root if the caller lives in the game, the DLC's root if the caller lives in a DLC. To reach the game from a Global-mode DLC, use @Game/....

The mode applies to require, load, and Asset.GetAsset / Asset.ImportAsset path resolution alike.

Folder-style modules — init.luau

Requiring a folder loads its init.luau: require("./ui") works if either ui.luau or ui/init.luau exists, with the file taking priority. Useful for grouping a feature into a folder while keeping a single import surface.

@self — init-aware

@self/X normally anchors at the caller's package root. But if the calling file is named init.luau, @self instead anchors at that init file's own folder. This makes init.luau behave like a Python __init__.py: feature folders become self-contained modules whose internal files reference each other through @self/... without caring about the rest of the package layout.

Examples

Worked examples assume this layout:

MyGame/                   # default package, "MyGame"
  Main.luau
  utils.luau
  ui/
    init.luau             # folder-style module: "@self/ui" or "./ui"
    button.luau
    icon.png

DLC/PhysicsDLC/           # a DLC package, ID "PhysicsDLC"
  ManagedInfo.toml
  init.luau
  rigid.luau
FromCallLoads
Main.luau require("./utils") utils.luau
Main.luau require("./ui") ui/init.luau (folder → init)
ui/init.luau require("./button") ui/button.luau
ui/button.luau require("../utils") utils.luau (Relative mode)
ui/init.luau require("@self/button") ui/button.luau (init-anchored)
ui/button.luau require("@self/utils") utils.luau (button isn't init, so @self = package root)
Main.luau require("@PhysicsDLC/rigid") DLC/PhysicsDLC/rigid.luau
PhysicsDLC/init.luau require("@Game/utils") game's utils.luau
any local p = Managed.GetPackage("PhysicsDLC")
require(p.Origin)		 DLC/PhysicsDLC/init.luau

Asset paths

The same @self / @Game / @PkgId rules apply to asset paths: 

-- from ui/init.luau:
local icon = Asset.GetAsset("Image", "@self/icon")        -- ui/icon.png
local hud  = Asset.GetAsset("Image", "@Game/ui.hud")       -- game's ui/hud.png
local rig  = Asset.GetAsset("Model", "@PhysicsDLC/rigid")  -- DLC asset

__dirname

__dirname string read-only

Absolute path of the calling script's directory. Each script sees its own value, not a single global, so relative paths can be built without coordinating with the rest of the project. 

local data = require(__dirname .. "/data/levels")
local img  = Asset.ImportAsset("Image", __dirname .. "/portrait.png")

Inside a packaged .managed bundle, __dirname is the script's vfs key, still works with require but isn't a real disk path. For raw filesystem access from inside a bundled script use Asset.ImportAsset instead of IO.read.

load

load(path) → any

Pull a Luau script in from the real filesystem and run it once, returning whatever the chunk returns (or true for bare side-effect scripts). Use this for mods, user-content scripts, hot-reloaded dev tools — anything that lives outside the project's bundled tree. For in-bundle modules use require.

Path forms

FormResolves to
"C:/mods/init.luau" Absolute Windows path.
"/usr/local/share/mod/x.luau" Absolute Unix path.
"./helper" Relative to the calling script's directory on disk (the caller's __dirname).
"./helper.luau" Same with explicit extension. If no extension is given the loader probes .luau then .lua.

What loaded scripts can do

Loaded scripts get a full Ruzit env (require, import, load, __dirname, print) with these resolution rules:

  • ./X and bare paths resolve relative to the loaded file's own directory on disk. So a script at C:/mods/foo.luau doing require("./bar") gets C:/mods/bar.luau — nested mod files just work without anyone hard-coding paths.
  • Global-mode hosts: if the host game's "File Type" = "Global", bare and ./-prefixed paths resolve from the game root instead of the loaded file's directory. Loaded scripts inherit the host's mode, the same way a DLC would.
  • @Game/X always reaches into the host game's bundle — the escape hatch a mod uses to require something from the game it's modding.
  • @PkgId/X reaches a specific loaded DLC / external package, same as from regular in-bundle scripts.
  • @self/X behaves like ./X: anchored at the loaded file's own directory, and at the loaded file's directory specifically when the loaded file is named init.luau.
-- main.luau (in the game)
local mod = load("C:/mods/init.luau")
mod.run()

-- C:/mods/init.luau
local util   = require("./util")        -- C:/mods/util.luau (filesystem-relative)
local hud    = require("@Game/ui/hud")   -- game's bundled ui/hud.luau
local physics = require("@PhysicsDLC/rigid") -- a loaded DLC
local Window = import("Window")        -- engine library
return { run = function() Window.Open() end }
Loaded scripts run with full engine privileges. They can open windows, read assets, talk to Steam — everything the host script can. Treat load'd code as part of your trust boundary; if you're loading user-supplied files, validate the path source before reaching for it.
Don't confuse with Lua's built-in load. Standard Lua has a load(string) function for evaluating source strings. Ruzit shadows it with the file-loading version above, so load("print('hi')") tries to read a file named print('hi') and fails. For in-memory text use Asset.FromString("File", ...).

print

print(...)

Tab-separated, newline-terminated stdout. Coerces every argument to a string via Lua's standard tostring rules, falling back to {...}-style debug formatting for non-coercible values (function references, etc.). 

print("player", player.name, "hp", player.hp)
Console attach. A windowed launcher built with exe-windowed = true in build.toml has no console by default, so print output goes nowhere. Pass --console on the command line to attach (or allocate) a console window for debugging. See CLI.
