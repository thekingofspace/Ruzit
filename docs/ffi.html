FFI

Load native libraries from disk and call into them from Luau. A Ruzit-loadable DLL is a Rust (or C/C++, or anything with C linkage) cdylib that exports two functions following the Ruzit FFI ABI. Used for hand-tuned hot loops, proprietary middleware, OS-specific tricks, and any time you need to step outside the Luau sandbox into native code your team controls.

Trust boundary. A loaded DLL has the full process privileges of the engine. Treat FFI.Load as you would dlopen — only load libraries you built or trust. Player mods should be handled through the Packages system, which loads Luau bytecode (sandboxed), not arbitrary native code. 
local FFI = import("FFI")

local lib = FFI.Load("ruzit_ffi_counter")

print(lib:Call("get"))                            -- 0
print(lib:Call("increment", { step = 5 }))       -- 5
print(lib:Call("echo", { hello = "world" }).hello) -- world
lib:Unload()

Library resolution

FFI.Load(name) looks for the native library in two places, in order:

  1. <project-root>/bin/ when running under ruzit test (the project root is the folder that owns build.toml).
  2. <exe>/bin/ in a built game (next to the launcher executable).
  3. <exe>/ directly, as a last-ditch fallback.

The filename is platform-specific:

Windows<name>.dll
Linuxlib<name>.so then <name>.so
macOSlib<name>.dylib then <name>.dylib

If name already has an extension, or is an absolute path, it's used verbatim. The dev / shipped layout is identical: 

-- during `ruzit test`
my-game/
    Main.luau
    build.toml
    bin/
        ruzit_ffi_counter.dll       -- found here

-- after `ruzit build`
Generated/
    MyGame.exe                      -- launcher
    Managed/...
    bin/
        ruzit_ffi_counter.dll       -- copied automatically from project bin/

FFI

FFI.Load(name) -> FFILibrary

Open a native library by name. Errors if the file can't be located, can't be loaded by the OS dynamic linker, or doesn't export both ruzit_ffi_call and ruzit_ffi_free. The returned handle stays alive until you call :Unload() on it or it falls out of scope (Luau GC drops the last reference and the OS unmaps the library).

FFI.BinDirectory() -> string?

Returns the resolved bin/ path, or nil when none exists. Useful for debug logs and for tooling that wants to surface the loader path.

FFI.List() -> { string }

Filenames inside the resolved bin/ that look like loadable native libraries (.dll / .so / .dylib). Order is filesystem-defined. Empty when no bin/ exists.

FFI.CallAsync(library, name, args?) -> any

Async sibling of library:Call. Spawns the DLL invocation on a worker thread and yields the calling coroutine via coroutine.yield(); the engine resumes it on a later frame once the worker has produced a JSON-parsed result. Must be called from inside a Task.Spawn / Task.Defer / Task.Delay coroutine — yielding from the top-level script errors with attempt to yield from outside a coroutine. The heart loop and every other coroutine keep running while the DLL is busy. 

Task.Spawn(function()
    local result = FFI.CallAsync(lib, "slow_compute", { ms = 800 })
    print("DLL done", result.elapsed_ms)
end)

Named signals (DLL → Luau callbacks)

The DLL can fire a named signal back into Luau via the Signal.Fire host RPC. Register the signal under a string name on the Luau side first; the FFI pump looks up the matching Signal instance on the main thread and fires it with the JSON args expanded into a MultiValue (arrays become positional arguments; a scalar or object becomes a single argument).

FFI.RegisterSignal(name, signal)

Bind a Lua Signal (from import("Signal").new()) to a string name. The DLL fires it with host_call("Signal.Fire", { name, args }). Re-registering the same name replaces the previous binding and drops the old Signal's registry slot. Connections persist across re-registration of a fresh Signal because they're attached to the Signal instance, not the name. 

local Signal = import("Signal")
local on_done = Signal.new()

FFI.RegisterSignal("ai.path_finished", on_done)
on_done:Connect(function(info)
    print("DLL says unit", info.unit_id, "reached the goal")
end)

-- on the rust side:
-- host_call("Signal.Fire", &json!({
--   "name": "ai.path_finished",
--   "args": [{ "unit_id": 42, "waypoints": 5 }],
-- }));
FFI.UnregisterSignal(name) -> boolean

Drop a previously-registered named signal. Returns true if a binding existed. Subsequent DLL Signal.Fire calls for that name log a warning to stderr but don't error.

Threading. Even when the DLL fires from a worker thread, the connected Luau handlers run on the main thread — the fire is queued in MAIN_TASK_QUEUE and applied in the next ffi::pump. Worst-case latency is one frame.

Shared k/v store

The engine maintains a HashMap<String, serde_json::Value> that both sides — Luau code and any loaded DLL — read and write. Use it as the "blackboard" for state owned by the DLL but readable by Luau, or vice versa: AI scratchpads, custom-object descriptors, save snapshots, profiler counters, quest flags exposed to native scripts, etc.

The DLL side calls World.Set / World.Get / World.Has / World.Delete / World.Keys through the RuzitHost vtable; the Luau side uses these helpers:

FFI.SetData(key, value)

Write a value under key. value can be any JSON-serialisable Luau type: nil, booleans, numbers, strings, arrays, tables, plus the engine's primitive userdata (Vector, Color3, CFrame) which are auto-tagged with _type so the DLL can dispatch on them. Mixed-key tables aren't supported — pick array or object. 

FFI.SetData("npc.7", {
    name      = "Borg",
    hp        = 42,
    home      = Vector.new(10, 0, 5),
    inventory = { "sword", "map", "potion" },
})
FFI.GetData(key) -> any

Read the value under key, or nil if absent. The result is decoded from JSON: objects come back as tables keyed by string, arrays as 1-indexed Luau tables. The _type-tagged Vector / Color3 / CFrame shapes come back as plain tables — reconstruct userdata yourself if you need it (Vector.new(t.x, t.y, t.z)). 

local npc = FFI.GetData("npc.7")
if npc and npc.hp < 10 then
    npc.alerted = true
    FFI.SetData("npc.7", npc)         -- write back; the DLL sees it next tick
end
FFI.HasData(key) -> boolean

Cheap existence probe — doesn't return / decode the value. Use to gate work behind keys the DLL hasn't populated yet.

FFI.DeleteData(key) -> boolean

Remove a key. Returns true if it was present. Both the Luau side and any loaded DLL see the key disappear immediately.

Concurrency. The world store sits behind a single Mutex; any Luau write blocks DLL workers reading the same key for the duration of the JSON serialisation (microseconds, normally). Don't park huge blobs in a single key — split per-entity state across multiple keys ("npc.7.hp", "npc.7.target", etc.) if a value gets large.

FFILibrary

.Alivebooleanread-only

True while loaded; false after :Unload().

.Sourcestringread-only

Filesystem path the library was opened from.

library:Call(name, args?) -> any method

Dispatch a named export on the loaded library. name is the string the Rust side dispatches on inside its ruzit_ffi_call (it doesn't have to be an actual exported symbol — just a key the single entry point recognises). args is any JSON-serialisable value: nil, boolean, number, string, an array table, or an object table. The engine encodes it as a JSON string, hands it to the DLL, parses the JSON string the DLL returns, and yields the matching Lua value. nil / null / an empty return string all become Lua nil.

Errors when the library has been unloaded, the args can't be serialised (mixed string+integer keys aren't supported — pick one), or the DLL returns malformed JSON.

library:GetNative() -> { [string]: any }? method

Return the native-mlua table the DLL populated during load, or nil if the DLL didn't export the optional ruzit_ffi_init_native. Values in this table are real mlua::Function / AnyUserData objects — not JSON shims — so the DLL can hand you userdata types it defined itself, and you can pass engine userdata (Vector, Color3, CFrame, etc.) straight in without marshalling. See the native bridge section for the full ABI and a worked example.

library:Unload()method

Drop the handle. The OS dlclose'es the library; subsequent :Call() attempts error. Idempotent. Caution: if you used the native bridge, any Lua function still reachable from GetNative()'s table becomes a dangling C function pointer after unload — clear or replace those entries first.

The Ruzit FFI ABI

A Ruzit-loadable library exports exactly two C-linkage functions: 

extern "C" fn ruzit_ffi_call(name: *const c_char, args: *const c_char) -> *mut c_char;
extern "C" fn ruzit_ffi_free(ptr: *mut c_char);
  • ruzit_ffi_call receives a NUL-terminated export name and a NUL-terminated JSON args string. It returns a NUL-terminated JSON result string allocated with CString::into_raw (or any allocator the same DLL can free).
  • ruzit_ffi_free reclaims the pointer the engine got from ruzit_ffi_call. Always the DLL's own allocator — do not free with Rust's Box::from_raw if you allocated with CString::into_raw on the engine side; ownership always stays inside the DLL.
  • Return std::ptr::null_mut() to indicate "no result" (Lua sees nil). The free function should treat null as a no-op.

Minimum viable Rust crate

Cargo.toml: 

[package]
name    = "myffi"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
serde_json = "1"

src/lib.rs: 

use std::ffi::{CStr, CString};
use std::os::raw::c_char;
use serde_json::{json, Value};

#[unsafe(no_mangle)]
pub extern "C" fn ruzit_ffi_call(
    name: *const c_char,
    args: *const c_char,
) -> *mut c_char {
    if name.is_null() { return std::ptr::null_mut(); }
    let name    = unsafe { CStr::from_ptr(name) }.to_string_lossy().into_owned();
    let args_s  = if args.is_null() { "null".into() }
                  else { unsafe { CStr::from_ptr(args) }.to_string_lossy().into_owned() };
    let parsed: Value = serde_json::from_str(&args_s).unwrap_or(Value::Null);

    let result = match name.as_str() {
        "add" => {
            let a = parsed.get("a").and_then(|v| v.as_f64()).unwrap_or(0.0);
            let b = parsed.get("b").and_then(|v| v.as_f64()).unwrap_or(0.0);
            json!(a + b)
        }
        other => json!({ "error": format!("unknown export: {other}") }),
    };

    CString::new(result.to_string()).map(|c| c.into_raw())
        .unwrap_or(std::ptr::null_mut())
}

#[unsafe(no_mangle)]
pub extern "C" fn ruzit_ffi_free(ptr: *mut c_char) {
    if !ptr.is_null() {
        unsafe { let _ = CString::from_raw(ptr); }
    }
}

cargo build --release, drop the produced library into your project's bin/, and call it from Luau: 

local lib = FFI.Load("myffi")
print(lib:Call("add", { a = 3, b = 4 }))  -- 7

A working version of exactly this pattern is in Examples/ (rust-ffi-counter/ + luau-ffi-counter/).

Native mlua bridge

Optional second ABI. When the JSON path feels too restrictive — you want to receive engine userdata and mutate it in place, define your own UserData types in Rust, or return real Lua functions — export ruzit_ffi_init_native alongside the JSON pair. The host hands the DLL a raw lua_State and a Lua table to populate; everything you put in the table is reachable from Luau via library:GetNative().

This ABI sacrifices isolation for ergonomics. The DLL links its own copy of mlua + Luau, but at runtime both binaries operate on the same lua_State. That requires the two mlua versions to be bit-compatible. Pin the version exactly (mlua = "=0.11.6"), don't ship a DLL built against a newer mlua than the host you're targeting, and treat the rules below as non-negotiable.

The extra export

extern "C" fn ruzit_ffi_init_native(
    state: *mut mlua::lua_State,
    table_name: *const c_char,
) -> bool;

Called once by the host immediately after ruzit_ffi_init (if it exists), inside the same FFI.Load call. The DLL gets back two things:

  • state — the host's *mut lua_State. Pass it to mlua::Lua::get_or_init_from_ptr(state) to get a &Lua handle on the existing state. The call is idempotent: mlua stores its bookkeeping (ExtraData) inside the lua_State itself, so the function just finds the host's existing binding and returns a reference to the same logical Lua instance.
  • table_name — a NUL-terminated key the host used to park a fresh empty Table in the named registry. Fetch it with lua.named_registry_value(&name) and populate it however you like. Everything you set here is reachable from Luau as library:GetNative().<name>.

Return true on success. Return false if something goes wrong — the host discards the table and library:GetNative() resolves to nil.

Worked example

Add mlua to your DLL's Cargo.toml with an exact-match pin: 

[dependencies]
serde_json = "1"
# Must match the host's mlua version exactly. ExtraData layout
# changes between mlua minor versions and a mismatch is UB.
mlua = { version = "=0.11.6", features = ["luau", "luau-jit"] }

Then implement ruzit_ffi_init_native. The example below defines a Point userdata with mutable X/Y fields, exposes a constructor, a free function that mutates an existing point, and a function that returns multiple values: 

use std::ffi::CStr;
use std::os::raw::c_char;

#[derive(Clone, Copy)]
pub struct Point { pub x: f32, pub y: f32 }

impl mlua::UserData for Point {
    fn add_fields<F: mlua::UserDataFields<Self>>(f: &mut F) {
        f.add_field_method_get("X", |_, p| Ok(p.x as f64));
        f.add_field_method_set("X", |_, p, v: f64| { p.x = v as f32; Ok(()) });
        f.add_field_method_get("Y", |_, p| Ok(p.y as f64));
        f.add_field_method_set("Y", |_, p, v: f64| { p.y = v as f32; Ok(()) });
    }
    fn add_methods<M: mlua::UserDataMethods<Self>>(m: &mut M) {
        m.add_method("Length", |_, p, _: ()| {
            Ok(((p.x * p.x + p.y * p.y) as f64).sqrt())
        });
        m.add_method_mut("Translate", |_, p, (dx, dy): (f64, f64)| {
            p.x += dx as f32;
            p.y += dy as f32;
            Ok(())
        });
    }
}

#[unsafe(no_mangle)]
pub unsafe extern "C" fn ruzit_ffi_init_native(
    state: *mut mlua::lua_State,
    table_name: *const c_char,
) -> bool {
    let name = unsafe { CStr::from_ptr(table_name) }
        .to_str().unwrap_or_default().to_string();
    let lua = unsafe { mlua::Lua::get_or_init_from_ptr(state) };
    let table: mlua::Table = match lua.named_registry_value(&name) {
        Ok(t) => t,
        Err(_) => return false,
    };

    // Constructor — returns a userdata defined by the DLL.
    table.set("Point", lua.create_function(|_, (x, y): (f64, f64)| {
        Ok(Point { x: x as f32, y: y as f32 })
    }).unwrap()).unwrap();

    // Receives a userdata, mutates it in place.
    table.set("Translate", lua.create_function(
        |_, (point, dx, dy): (mlua::AnyUserData, f64, f64)| {
            let mut p = point.borrow_mut::<Point>()?;
            p.x += dx as f32;
            p.y += dy as f32;
            Ok(())
        }
    ).unwrap()).unwrap();

    // Returns multiple Lua values.
    table.set("ToPolar", lua.create_function(|_, point: mlua::AnyUserData| {
        let p = point.borrow::<Point>()?;
        let r = ((p.x * p.x + p.y * p.y) as f64).sqrt();
        let theta = (p.y as f64).atan2(p.x as f64);
        Ok((r, theta))
    }).unwrap()).unwrap();

    true
}

Call it from Luau: 

local lib = FFI.Load("myffi")
local native: any = lib:GetNative()

local p = native.Point(3, 4)
print(p.X, p.Y, p:Length())   -- 3, 4, 5

p:Translate(10, 0)             -- DLL-defined method, mutates p
native.Translate(p, 0, 5)        -- DLL-defined free function, also mutates p

local r, theta = native.ToPolar(p)
print(r, theta)                  -- multi-return works

Accepting engine userdata

Because the DLL is talking to the host's lua_State directly, any userdata Luau hands you arrives as a real mlua::AnyUserData. You can :borrow_mut::<T>() the engine's types directly — Vector, Color3, CFrame, etc. — if your DLL can name the type (i.e. depends on a shared types crate, or you re-declare the same struct layout). For loose interop you can also use AnyUserData::user_value::<T>() / :has_metatable_field() to inspect without committing to a concrete type.

Engine-defined types you can borrow from a DLL without redeclaring:

  • crate::libs::primitives::Vector
  • crate::libs::primitives::Color3
  • crate::libs::primitives::CFrame
  • crate::libs::primitives::Dim

To borrow them by name your DLL would need a Cargo dependency on the runtime crate, which couples your build to the host. For most cases you'll either define your own userdata types or pull the fields out via AnyUserData::get(&str) and rebuild a Vector on the way back.

Rules — non-negotiable

  1. mlua version must match exactly. Pin with = in Cargo.toml. A mismatch shifts the ExtraData layout inside the shared lua_State and causes undefined behaviour the moment either side accesses internal mlua state. There is no runtime check; the only protection is the pin.
  2. Never store an mlua::RegistryKey across binaries. Each binary has its own registry-ID counter and drop tracking. If the DLL creates a key the host can't safely drop it, and vice-versa. Pass values by reference through the populated table only.
  3. Treat :Unload() as terminal. Lua functions registered by the DLL are backed by C function pointers in the DLL. After :Unload() those pointers are dangling — calling one is a crash. Either don't unload, or first overwrite each entry on the native table with nil from Luau before unloading.
  4. One thread only. All mlua calls (host and DLL) must happen on the main Lua thread. If you do background work in the DLL, marshal results back via Signal.Fire on the host RPC path (which is thread-safe) rather than touching the Lua state directly.
  5. Errors are caught. Returning an Err from a registered function turns into a Lua-side error(), so normal pcall/xpcall works around DLL calls just like any other Lua function.

When to use which ABI

If you want…Use
Pure-data calls. Simple in/out, no shared state, the DLL can be rebuilt independently of the host. JSON ABI (ruzit_ffi_call + library:Call)
To mutate engine userdata (a Vector, a Primitive, a CFrame) in place without copying through JSON. Native bridge (library:GetNative())
To define your own UserData type with custom fields and methods that feel native in Luau (p:Translate(dx, dy) etc.). Native bridge
To return multiple values, real functions, or tables-of-functions from a DLL call. Native bridge
To call back into the engine (Primitive.SetPosition, etc.) from a worker thread. Host RPC catalog (host vtable received in ruzit_ffi_init) — both ABIs support it; the JSON ABI doesn't preclude using the host vtable.

The two ABIs coexist freely: a DLL can export ruzit_ffi_call + ruzit_ffi_free for the JSON path and ruzit_ffi_init_native for the native table, and Luau can mix lib:Call("fast_path", args) with lib:GetNative().rich_path(userdata) on the same library. The rust-ffi-counter example does exactly that.

Signal (DLL fires named signals back into Luau)

Luau side registers a Signal under a string name: 

local Signal = import("Signal")
local sig    = Signal.new()
FFI.RegisterSignal("ai.path_finished", sig)
sig:Connect(function(info) print("DLL says:", info.unit_id) end)

DLL calls Signal.Fire. The pump fires the signal on the main thread with the JSON args expanded into MultiValue (arrays become positional arguments; scalars / objects become a single argument).

Signal.Fire { name, args } args is null, a single value, or an array. Queued -- the call returns immediately on the DLL side with null; the actual fire happens on the next FFI pump.

World (cross-thread JSON k/v)

A shared HashMap<String, serde_json::Value> both sides read and write. Use for "custom object" state the DLL owns but Luau needs to introspect (or the reverse).

World.Set{ key, value }
World.Get{ key }Returns the stored value, or null.
World.Has{ key }Boolean.
World.Delete{ key }Boolean (was present).
World.KeysnullArray of strings.

Luau-side helpers: FFI.SetData(key, value), FFI.GetData(key), FFI.HasData(key), FFI.DeleteData(key).

What auto-marshals as a handle

When passing one of these userdata to library:Call, the engine registers it in FFI_HANDLES (Arc-deduped) and the DLL receives a stable id it can use across calls:

GUI Primitive{ _type: "PrimitiveHandle", _handle }
BasePart{ _type: "PartHandle", _handle }
DrawableImg{ _type: "DrawableImgHandle", _handle }
Vector / Color3 / CFrametagged value JSON, no handle (pure value type)
Threading. Sync RPCs (Primitive/BasePart/DrawableImg mutators) lock the underlying Arc<Mutex<State>> on whatever thread calls them — safe because the engine only ever reads those POD fields. Anything that needs Lua (Signal.Fire, Camera.Set) is queued through MAIN_TASK_QUEUE and drained on the main thread by ffi::pump, so connected handlers and the thread-local camera state are touched exactly once per frame on the main thread.

Shipping a package that owns an FFI DLL

When a Package or DLC needs its own Rust DLL:

  1. Put a bin/ folder at the root of the package's folder. Anything in there is automatically copied to Generated/bin/ at build time, merged with the host project's bin/.
  2. Namespace your DLL filename (ruzit_ffi_yourpackage_thing.dll) so multiple installed packages don't collide on a generic name like core.dll.
  3. The package's Luau side calls FFI.Load using whatever stem you chose — same in dev and in shipped games.
