Extending the engine

Most of Ruzit's API surface is a fairly thin Lua-facing wrapper around Rust subsystems that already live in the runtime. Adding your own import("...") means writing a Rust module, registering it in three places, and exposing types from Luau. This page walks through the recipe and the perf rules the existing modules follow so a new one fits in cleanly instead of becoming the bottleneck.

Audience. This is for engine contributors, not game scripters. If you only want to call existing imports from Lua you don't need anything here — read the per-module pages in the API Reference instead.

Source layout

Everything that ships in a Ruzit binary lives under one workspace:

Ruzit/
  core/                  -- shared types: vfs, config, package format
  runtime/               -- the actual engine
    src/
      main.rs            -- entrypoint (ruzitrun)
      lib.rs             -- library entry (ruzit)
      runtime.rs         -- import() dispatch + module loader
      heart.rs           -- per-frame loop (heartbeat)
      errors.rs          -- pretty error formatting + IMPORT_LIBS list
      libs.rs            -- pub mod for every Lua-facing import
      libs/
        renderable/      -- e.g. import("Renderable")
        physics/         -- e.g. import("PhysicsService")
        keyboard/        -- ...etc
  cli/                   -- ruzit (scaffold, run, build, self-update)

Two binaries are produced from the same workspace: ruzit (the CLI front-end) and ruzitrun (the engine). The engine library is also re-exported from lib.rs so a published game's exe can statically link it — that's how the launcher boots without a separate runtime install.

Adding a new import (the eight-step recipe)

We'll walk through adding import("Clock") exposing a single function Clock.Now() that returns wall-clock seconds. Real modules do more, but the wiring is identical.

1. Write the module

Create runtime/src/libs/clock.rs:

use mlua::{Lua, Table};

pub fn create(lua: &Lua) -> mlua::Result<Table> {
    let t = lua.create_table()?;
    t.set(
        "Now",
        lua.create_function(|_, _: ()| -> mlua::Result<f64> {
            let now = std::time::SystemTime::now()
                .duration_since(std::time::UNIX_EPOCH)
                .map(|d| d.as_secs_f64())
                .unwrap_or(0.0);
            Ok(now)
        })?,
    )?;
    Ok(t)
}

The pattern every module follows: a pub fn create(lua) -> Result<Table> that builds and returns the Lua table users will see. The returned table is what import("Clock") resolves to, so set every entry you want exposed on it.

2. Declare the module in libs.rs

// runtime/src/libs.rs
pub mod clock;

Alphabetical-ish order, nothing magical.

3. Wire dispatch in runtime.rs

The install_import function is one big match over the name: String the user passed to import(...). Add a branch: 

// runtime/src/runtime.rs, inside install_import's match
"Clock" => libs::clock::create(lua)?,

The result is cached per script-environment via a RegistryKey map so the second import("Clock") in the same module returns the same table without rebuilding it.

4. Register in errors.rs (IMPORT_LIBS)

The error formatter shows a "did you mean...?" suggestion when a script imports an unknown name. Add yours to the list so a typo like import("Cloak") surfaces a hint: 

// runtime/src/errors.rs
pub const IMPORT_LIBS: &[&str] = &[
    "Actor", "Asset", "Clock", "Debug", /* ... */
];

5. Hook the heart loop (optional)

If your module has state that needs to advance every frame — queues to drain, signals to fire, timers to tick — expose a pub fn pump(lua: &Lua) or pub fn tick(lua: &Lua, dt: f64), and call it from heart::run_loop in heart.rs. Order matters: pumps run before the heart handlers fire so user code sees fresh state. Clock.Now() is stateless, so no hook needed.

6. Add the Luau type in types.d.luau

The shipped LSP definition file. Adding your module here is what makes the editor offer completion, hover docs, and type-check calls. Place it in the same area as siblings — one export type for the module's public API plus a line in the master _RuzitImports map: 

export type Clock_API = {
    -- Wall-clock seconds since the Unix epoch.
    Now: () -> number,
}

-- in the import dispatch type
Clock: Clock_API,

7. Optional: write a docs page

Anything user-facing belongs in docs/. Copy one of the smaller modules (debug.html, keyboard.html) as a template, replace the member-list entries, and add a line to _sidebar.html so it shows up in the API Reference column. The sidebar is rendered by sidebar.js — no per-page edits beyond that.

8. Build & test

cargo build --release
target/release/ruzitrun path/to/your/project.luaurc

From Luau: 

local Clock = import("Clock")
print(Clock.Now())

Patterns to mirror

The existing modules share a small handful of conventions. New modules that ignore them tend to leak, deadlock, or burn frame budget in ways that don't show up until shipping.

State lives in thread_local!

Ruzit is single-threaded at the Lua level. Module state is typically a thread_local! { static FOO: RefCell<...> = ... } rather than a global Mutex. This keeps everything cheap (no atomics on the hot path), and the main loop owns the only thread that touches it. See libs/window/mod.rs, libs/signal/mod.rs, or libs/runservice/mod.rs for the pattern.

Work that must happen on another thread (audio capture, the rayon physics pool, the network thread) communicates with the main thread through an Arc<Mutex<T>> that the main loop drains each frame — never the other way around. The SoundByte voice channel and the Net queue are good worked examples.

Userdata wraps a small handle, not the whole state

For things with identity (a part, a physics object, a controller), the pattern is: 

pub struct PartState { /* all the heavy state */ }

pub struct PartHandle {
    pub state: Arc<Mutex<PartState>>,
}

The userdata PartHandle is a tiny clone-cheap thing Lua hands around. Methods lock the Arc<Mutex<...>>, do their work, release. This makes Lua-side cloning free, scoped locks short, and lifetime simple — if every userdata referencing a state drops, the Arc count hits zero and the state cleans up on its own.

Signals are Tables, not Functions

Every event you want script to :Connect to is a Signal instance from libs::signal::new_instance(lua). Don't invent your own callback list; you'd reinvent threading, error isolation, and disconnect bookkeeping. Hand the Signal table back out through the userdata's add_field_method_get.

Per-tick "pump" pattern

Rather than firing signals from inside locks or from worker threads, modules push events into a queue and the main loop drains the queue once per frame. Look at libs/window/mod.rs: WindowApp::window_event pushes WindowChange values into app.pending; pump() drains the vec after pump_app_events returns and only then fires Lua signals. Same shape for soundbyte byte routes, keyboard input, gamepad input, etc.

Cache snapshots, not direct reads

The GUI snapshot, the renderable parts snapshot, and the physics GPU buffer pack all follow the same idea: a global version counter is bumped any time something visible changes, and the next snapshot read rebuilds only if the counter moved. Look at libs/gui/mod.rs — GUI_VERSION / bump_dirty / SNAPSHOT_CACHE. A new module that draws something every frame should follow the same shape so frames where nothing changed are free.

GPU resources keyed by id and version

A subtle one. When the same logical asset (a Model, a deformed Part) can change underneath you, the GPU cache must key on both the stable id and a version counter you bump every time the underlying data is rewritten. The pre-version cache used to early-return on id match alone, which silently broke DistortionBox and animation deformation — we'd hand back the stale vertex buffer for an unchanged id. The fix lives in libs/renderable/mod.rs (ModelRef.version) and libs/gui/render.rs (ensure_model_buffers).

Performance techniques used in the engine

Single Lua thread, JIT enabled

Compiler::new().set_optimization_level(2).set_debug_level(1) plus enable_jit(true) at startup (runtime::run_entry). Luau's JIT is fast, and the compiler's higher optimization level produces tighter bytecode for hot loops. The slight increase in compile time is paid once per module load, before the heart loop starts.

Bytecode bundling for shipped games

ruzit build compiles every .luau in the project to bytecode and packs it (plus assets) into a single encrypted, zstd-compressed .managed bundle. At runtime the engine mmap'd-equivalent reads modules from the bundle, skipping disk I/O and source compilation entirely. See core/src/package.

Asset cache + reference counting

Asset.GetAsset returns the same userdata for the same key — the byte buffers (and decoded image / model data) live behind Arcs that are reused across callers. :Free() drops the strong ref the cache holds; the Arc survives as long as something else points at it, so an in-flight Sound keeps playing even after the SoundData has been freed. See libs/asset/mod.rs.

Override cells for physics ↔ renderable

Physics writes hundreds of CFrames per tick; locking each BasePart's main Mutex<PartState> per write would serialize against script accessors. The fix: physics_override: Option<Arc<Mutex<CFrame>>> on each PartState. Physics writes to that small cell; reading part.CFrame from Luau transparently returns the simulated value. The heavy state mutex never gets touched on the hot path. See libs/physics/mod.rs and the CFrame getter on PartHandle.

Live signal fire from inside winit callbacks

The window resize path stashes a *const Lua in a thread-local while pump_app_events is running so WindowEvent::Resized can fire SizeChanged live — including from inside Win32's modal drag loop. Without that, resize events would queue behind the modal loop and not fire until the user released the mouse. See libs/window/mod.rs (ACTIVE_LUA, try_fire_live).

Camera link runs after physics, before render

Order in heart::run_loop matters. Physics writes its final CFrames to its bodies; then renderable::tick_camera_link reads them; then animations, drawables, GUI. So a third-person camera following a Controller never lags a frame behind. The same ordering rule applies to anything that reads physics output — tween targets, particle emitters anchored to bodies, audio Follow-targets.

Parallel physics step via rayon

Each PhysicsPlane can own a ThreadPool sized at construction (opts.Threads). Rapier's solver runs against that pool, so heavy planes parallelize without leaking threads into smaller ones. The pool is Arc'd so a plane teardown only drops the pool when no in-flight solve still references it.

GPU physics for small simulation pockets

Planes with DeferGpu = true route their step through a compute shader (libs/physics/mod.rs's step_plane_gpu). Useful for clouds of light, non-collidable bodies. The CPU path stays in charge for interactive collision, contact constraints, and pinned objects.

Per-glyph palette baking for styled text

GUI text supports {#RRGGBB} inline color escapes without re-rasterising glyphs per run. The bake walks color runs once, lays them out with fontdue's user_data field carrying the palette index, and writes the final RGBA bitmap using a palette lookup on the alpha mask. See libs/gui/mod.rs (parse_color_runs, bake_text).

Mutex split: keep CFrame reads off the hot mutex

A recurring theme. If a tight loop reads one field, that field gets its own Mutex (or an Arc<Mutex<...>> on a sub-state) so the big-state mutex isn't fought for. The physics_override cell is one example. The voice channel's threshold + level meters living in their own Mutex<f32> while the rest of the channel is locked separately is another.

Cheap signal delivery

Signal connections are Arc<Function> stored in a Vec on the Signal table. Firing walks the vec and resumes each callback as its own Lua thread, isolated — one connection erroring doesn't break the rest. Each connection is identified by a generation id so disconnect is O(n) but cheap; no rehashing. The pump pattern (drain into a temp vec, fire outside locks) keeps re-entrant :Connect / :Disconnect calls from invalidating iterators.

What not to do

  • Don't fire signals from inside a held lock. Connections run user Lua. User Lua can lock anything. You will deadlock. Drain into a temp vec, drop the lock, then fire.
  • Don't hold an APP.borrow_mut() across a user callback. Every window helper that reads APP.borrow() will panic. Use a side cell (see CURRENT_WINDOW in window/mod.rs) when you need read access during pumping.
  • Don't store a RegistryKey for a callback without dropping it on teardown. mlua registry keys are reference-counted on the Lua side; leaking them means the function (and its upvalues) lives forever.
  • Don't lock the same Arc<Mutex<...>> twice on the same thread. Easy to do accidentally when a helper takes &Arc<Mutex<T>> and the caller already holds the guard. Pass &T or &mut T through.
  • Don't rebuild GPU buffers every frame. Use the id+version pattern. Treat re-uploads as the exception, not the rule.
  • Don't allocate inside the heart loop's tight paths. Reuse Vecs with clear() + push. Avoid format!() on the hot path; use it for error messages only.
  • Don't introduce a new Cargo.toml dependency without considering the build-time and binary- size cost. The engine ships as a single statically-linked binary; every dep widens both. Optional features (#[cfg(feature = "voice")]) are the right tool for heavyweight optional deps.

Reading list

Best examples to read before adding a non-trivial module:

  • libs/window/mod.rs — thread-local state, live signal fire from inside winit callbacks, the side-cell trick that lets script query window state during a pump.
  • libs/signal/mod.rs — how Signals are implemented; the connect-disconnect-fire dance.
  • libs/physics/mod.rs + libs/physics/controller.rs — many small sub-locks, override cells, the per-plane ThreadPool, the rapier query-pipeline ground probe used by the controller.
  • libs/soundbyte/mod.rs — complex multi-source / multi-sink graph routing, per-device cpal stream rebuild, and the link-handle pattern that supports many concurrent chains.
  • libs/asset/mod.rs — reference-counted loader with typed loaders per kind and the keyof<> / index<> generic pattern that types it on the Luau side.
  • libs/gui/mod.rs — snapshot caching keyed on a version counter; the styled-text bake pipeline.
