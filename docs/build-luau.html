build.luau

Scriptable build configuration. Lives at the root of every project next to Main.luau. Runs at build time only — ignored by the runtime in packaged games. Replaces build.toml; if both files exist build.luau wins.

Example

--!strict

build.name = "My Game"
build.version = "0.1.0"
build.creator = "me"

build.ExeName = "MyGame"
build.Windowed = true
build.FileType = "Relative"

for _, pkg in ipairs(build:GetPackages()) do
    pkg.CompressScripts = true
    pkg.ConvertToByte = false
    pkg.EncryptionToken = ""

    local main = pkg:CreateShard(1)
    local heavy = pkg:CreateShard(2)

    pkg:ParseAssets(function(asset, size)
        if size > 32 * 1024 * 1024 then
            return heavy, true, "xor"
        end
        return main, true
    end)
end

build

build is a global injected by the build harness. Assign to its fields up front, then iterate build:GetPackages() to configure each package — the project itself plus any DLC folders and external Packages/ entries.

FieldTypeNotes
namestringDisplay name written into the launcher trailer.
versionstringFree-form version string.
creatorstringAuthor / studio name.
ExeNamestringStem for the output executable (default: entry script stem). Also becomes the default package id.
Iconstring?Looks for <Icon>.ico next to build.luau and embeds it as the Windows exe icon. No-op on Linux/macOS builds.
WindowedbooleanDefault true. When false, the launcher is built with a console subsystem (Windows) or stdout-attached binary (Linux/macOS).
FileType"Relative" \| "Global"Default require/Asset path mode for the project. See globals.
SteamIDnumber?Steam app id baked into the launcher.
include{string}Extra files/folders copied verbatim next to the exe at build time. bin/ is auto-copied; don't list it.
GetPackages(self)() -> {package}Returns one handle per package on disk: the project plus every DLC folder and external Packages/ entry.

package

Each entry from build:GetPackages() exposes settings that apply at build time for that package's .scripts.managed and .assets.managed shards.

Field / MethodTypeNotes
idstringRead-only. The package id (e.g. the project's ExeName or each DLC's ManagedInfo.toml ID).
EncryptionTokenstringPer-package secret mixed into the per-asset XOR key. Built into the .managed file when written.
CompressScriptsbooleanzstd-compress every .luau/.lua before encryption.
ConvertToBytebooleanPre-compile scripts to Luau bytecode at build time. Faster startup, smaller files, source no longer recoverable.
CreateShard(self, id)(self, number) -> shardDeclares a shard with a given numeric id and returns a handle. Shard ids must form a contiguous run starting at 1 — you can declare them out of order (3, 1, 2 is fine; 4, 1, 2 errors).
ParseAssets(self, cb)(self, fn) -> ()Walks the package's assets/ folder, calling cb(asset, size) for each file. The callback returns (shard, compress, encryption); returning nil drops the asset from the build with a warning.

ParseAssets callback

pkg:ParseAssets(function(asset, size)
    -- asset: "@PackageID/relative/path.ext"
    -- size:  file size in bytes
    return shard, compress, encryption
end)
  • shard — the handle returned by pkg:CreateShard. Must belong to the same package. Return nil to skip.
  • compress — true to zstd-compress this asset before encryption. Optional, defaults to false.
  • encryption — ""/"none" stores plaintext; "xor" applies the per-package EncryptionToken XOR after compression. Optional, defaults to "".

shard

Opaque handle returned by pkg:CreateShard. Carries the parent package id and shard number; return it from ParseAssets to route an asset into the corresponding <id>.assets.shardNNNN.managed file.

Flags — gating shards and packages at runtime

By default, calling manifest.LoadManaged(id) at runtime pulls every shard from the package into memory. For large DLCs with many shards (per-chapter assets, optional language packs, high-res texture variants), that's wasteful. Flags let you mark individual shards — or whole packages — as opt-in: they ship in the build but stay dormant until the running game calls manifest.CallFlag(name). 

for _, pkg in ipairs(build:GetPackages()) do
    local always = pkg:CreateShard(1)
    local chapter_2 = pkg:CreateShard(2)
    local chapter_3 = pkg:CreateShard(3)
    local hires_skins = pkg:CreateShard(4)

    chapter_2:ListenToFlag("chapter_2")
    chapter_3:ListenToFlag("chapter_3")
    hires_skins:ListenToFlag("hd_textures")

    pkg:ParseAssets(function(asset, size)
        if asset:match("^@Game/levels/ch2_") then return chapter_2, true end
        if asset:match("^@Game/levels/ch3_") then return chapter_3, true end
        if asset:match("_hd%.png$") then return hires_skins, true end
        return always, true
    end)
end

With the build above, manifest.LoadManaged("@Game") loads shard 1 immediately. Shards 2, 3, and 4 only load when the game calls manifest.CallFlag("chapter_2") / "chapter_3" / "hd_textures" respectively. Until then, any Asset.GetAsset for an asset that lives inside one of those shards behaves as if the asset doesn't exist.

shard:ListenToFlag(flag)

Mark this shard as flag-gated. The shard is built into the final .managed drop but won't be deserialized at LoadManaged time. Multiple flags on the same shard means any of those flags activates it. Multiple shards can share the same flag — one CallFlag loads all of them.

pkg:ListenToFlag(flag)

Package-level gating. Calling manifest.CallFlag(flag) will auto-activate the entire package (runs the equivalent of manifest.LoadManaged) and then load its unflagged shards plus any of its shards that also listen to the flag. Useful when you want one game-side call to bring up a whole DLC — e.g. a "chapter 2" flag that pulls in the chapter's package and that package's optional high-res shard in one go.

Sharing one flag across many shards and packages

Flags fan out. The same flag string can be attached to any number of shards across any number of packages — one CallFlag activates all of them. This is the load- bearing primitive for content packs: 

-- in @PackageA/build.luau (or each DLC's own build evaluation)
pkg:ListenToFlag("commonutils")

-- in @PackageB/build.luau
pkg:ListenToFlag("commonutils")

-- in @PackageC/build.luau
local opt_shard = pkg:CreateShard(2)
opt_shard:ListenToFlag("commonutils")

Then from your game code: 

manifest.CallFlag("commonutils")
-- → activates PackageA + PackageB
-- → loads shard 2 from PackageC
-- → loads any matching shards from packages already active

Mix freely: one flag can hit package-level handlers and shard-level handlers in the same call. The CallFlag return value tells you exactly what fired (activated, loaded, errors).

Notes

  • An unflagged shard always loads when its package activates — flags only opt out of eager loading, never in.
  • @Game (the default project package) behaves the same as any other package: unflagged shards load at boot, flagged shards wait for CallFlag.
  • After pkg:Free(), all of that package's loaded assets get dropped — flag-loaded shards revert to dormant and must be re-activated with another CallFlag.
  • Calling a flag that nothing listens to is a silent no-op. Same flag called twice is idempotent — already-loaded shards aren't reloaded.

Cross-platform output

A single ruzit build invocation can emit Windows and Unix launchers in one go. The CLI scans its own directory for runtime binaries and produces one launcher per binary it finds — the build.luau script itself doesn't need to change.

Binary presentProducesIn Generated/
ruzitrun.exeWindows launcher<ExeName>.exe
ruzitrunLinux/macOS launcher<ExeName>

The Managed/ folder (shards, scripts, manifest) is shared between launchers — only the executable is platform-specific. Drop both binaries next to the CLI and you get a Windows + Linux drop from a single build. See ruzit build for the platform caveats (icon embedding still needs a Windows host).

Notes

  • build.luau is build-time only; the runtime never executes it.
  • If both build.luau and build.toml exist, build.luau is preferred and build.toml is silently ignored.
  • External Packages (under Packages/) and DLC folders show up in GetPackages() alongside the project. You can give each its own shard layout / encryption.
  • Manifest activation at runtime — only the default @Game package is auto-loaded. See manifest.LoadManaged.
