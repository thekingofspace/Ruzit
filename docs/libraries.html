Building libraries

A Ruzit library is a Rust (or C/C++) native library — cdylib — that the engine can load at runtime via FFI.Load and call into from Luau. Use one when you need code your game can't reasonably express in Luau: hand-tuned simd / SAT solvers, FFI to a proprietary middleware SDK, real-time DSP, ML inference, or anything else where you'd otherwise lower into C.

This page walks you through writing one end-to-end. The runtime reference for the API surface lives in FFI — if you only want to know what host RPCs the engine exposes, jump there. If you want to know what to put in your DLL and how to ship it, you're in the right spot.

Prerequisites

  • A Rust toolchain — stable, current edition.
  • The Ruzit CLI on your PATH (ruzit --version).
  • Optional: read the FFI reference once for the host RPC catalog.

Project layout

Keep the library project beside (not inside) your game project so its build artifacts stay separate. The convention used by the sample at Examples/rust-ffi-counter/ is: 

my-game/
    build.toml
    Main.luau
    bin/                         -- compiled DLLs land here
    bin/ruzit_ffi_audio.dll
my-libraries/
    audio/
        Cargo.toml
        src/lib.rs               -- the cdylib
        README.md
    pathfinder/
        Cargo.toml
        src/lib.rs

Per-library, the Cargo.toml only needs three things to set up correctly: 

[package]
name    = "ruzit_ffi_audio"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]            -- produce a loadable .dll/.so/.dylib
name       = "ruzit_ffi_audio"     -- match the FFI.Load name

[dependencies]
serde_json = "1"                  -- the wire format on both sides

The ABI in one screen

A Ruzit-loadable library exports two mandatory C-linkage functions and one optional one. That's the entire interface: 

// 1. mandatory: dispatch a named export.
extern "C" fn ruzit_ffi_call(name: *const c_char, args: *const c_char) -> *mut c_char;

// 2. mandatory: free the result string the engine got back.
extern "C" fn ruzit_ffi_free(ptr: *mut c_char);

// 3. optional: receive a RuzitHost vtable so the library can call
//    back into the engine (mutate primitives, fire signals, read
//    Camera state, paint into a DrawableImg, etc.).
extern "C" fn ruzit_ffi_init(host: RuzitHost);
  • Names are dispatch keys, not separate exports. You write one ruzit_ffi_call with a match name.as_str() inside; the Luau side picks which arm runs by passing the matching string to library:Call("name", ...). No need for per-function symbols.
  • JSON in, JSON out. Both args and result are NUL-terminated UTF-8 JSON. null / std::ptr::null_mut() means "no result", which Luau sees as nil.
  • The DLL owns its allocator. Allocate the return string with CString::into_raw; the engine hands the pointer back to your ruzit_ffi_free when it's done reading. Don't try to free what the engine passed you — only what you produced.

Minimum viable library

An add function that takes two numbers and returns the sum:

use std::ffi::{CStr, CString};
use std::os::raw::c_char;
use serde_json::{json, Value};

#[unsafe(no_mangle)]
pub extern "C" fn ruzit_ffi_call(name: *const c_char, args: *const c_char) -> *mut c_char {
    if name.is_null() { return std::ptr::null_mut(); }
    let name = unsafe { CStr::from_ptr(name) }.to_string_lossy().into_owned();
    let args = if args.is_null() { "null".into() }
               else { unsafe { CStr::from_ptr(args) }.to_string_lossy().into_owned() };
    let parsed: Value = serde_json::from_str(&args).unwrap_or(Value::Null);

    let result = match name.as_str() {
        "add" => {
            let a = parsed.get("a").and_then(|v| v.as_f64()).unwrap_or(0.0);
            let b = parsed.get("b").and_then(|v| v.as_f64()).unwrap_or(0.0);
            json!(a + b)
        }
        other => json!({ "error": format!("unknown: {other}") }),
    };

    CString::new(result.to_string()).map(|c| c.into_raw())
        .unwrap_or(std::ptr::null_mut())
}

#[unsafe(no_mangle)]
pub extern "C" fn ruzit_ffi_free(ptr: *mut c_char) {
    if !ptr.is_null() {
        unsafe { let _ = CString::from_raw(ptr); }
    }
}

cargo build --release, copy target/release/ruzit_ffi_audio.dll (or the .so / .dylib equivalent) into your game's bin/, and from Luau: 

local lib = FFI.Load("ruzit_ffi_audio")
print(lib:Call("add", { a = 3, b = 4 }))     -- 7

Holding state across calls

The DLL is a normal Rust crate; use OnceLock, Mutex, or any other concurrency primitive to keep state between ruzit_ffi_call invocations. The DLL is loaded once and stays mapped until the engine unloads it (or the process exits), so a static survives every call. 

use std::sync::Mutex;

static COUNTER: Mutex<i64> = Mutex::new(0);

// inside ruzit_ffi_call:
"increment" => {
    let mut c = COUNTER.lock().unwrap();
    *c += 1;
    json!(*c)
}

Concurrent calls into the library are possible — the engine may pump library:Call from the main thread and FFI.CallAsync simultaneously from a worker. Guard shared state with a mutex. Pure functions (no shared state) need nothing.

Calling back into the engine

Implement ruzit_ffi_init to receive a RuzitHost vtable, then call into it whenever the library wants to mutate engine state directly: 

use std::sync::OnceLock;

#[repr(C)]
#[derive(Clone, Copy)]
pub struct RuzitHost {
    pub call: extern "C" fn(name: *const c_char, args: *const c_char) -> *mut c_char,
    pub free: extern "C" fn(ptr: *mut c_char),
}

static HOST: OnceLock<RuzitHost> = OnceLock::new();

#[unsafe(no_mangle)]
pub extern "C" fn ruzit_ffi_init(host: RuzitHost) {
    let _ = HOST.set(host);
}

fn host_call(name: &str, args: &Value) -> Value {
    let host = HOST.get().expect("ffi_init wasn't called");
    let name_c = CString::new(name).unwrap();
    let args_c = CString::new(args.to_string()).unwrap();
    let ret = (host.call)(name_c.as_ptr(), args_c.as_ptr());
    if ret.is_null() { return Value::Null; }
    let s = unsafe { CStr::from_ptr(ret) }.to_string_lossy().into_owned();
    (host.free)(ret);
    serde_json::from_str(&s).unwrap_or(Value::Null)
}

Use it to mutate any engine object the Luau side handed you a handle for: 

// inside ruzit_ffi_call("orbit_part", &parsed):
let handle = parsed.get("part").and_then(|p| p.get("_handle"))
    .and_then(|v| v.as_u64()).unwrap();
host_call("BasePart.SetCFrame", &json!({
    "handle":   handle,
    "position": { "x": 10.0, "y": 0.0, "z": 0.0 },
    "rotation": { "x": 0.0,  "y": 0.0, "z": 0.0 },
}));

See the Host RPC catalog for the full list of RPC names and their JSON shapes (Primitive, BasePart, DrawableImg, Camera, Signal, World).

Long-running and async work

A ruzit_ffi_call that takes more than a few ms should not block the engine. Two patterns:

From the Luau side: FFI.CallAsync

Wrap the call in a coroutine; FFI.CallAsync yields the calling coroutine and resumes it when the worker returns: 

Task.Spawn(function()
    local result = FFI.CallAsync(lib, "build_navmesh", mesh_data)
    print("navmesh ready", result)
end)

The DLL function still runs synchronously inside ruzit_ffi_call — just on a worker thread the engine spawned. Use this when the Luau side wants to wait on the result.

From the DLL side: spawn your own thread

Sometimes the DLL wants to do work over time (animate a part, poll a network socket, stream audio). Return immediately from ruzit_ffi_call with a "started" reply, then drive progress from a thread the DLL spawned itself, calling host.call as needed: 

"start_simulation" => {
    let handle = parsed.get("part").and_then(...);
    std::thread::spawn(move || {
        for tick in 0..1000 {
            host_call("BasePart.SetCFrame", &json!({ ... }));
            std::thread::sleep(std::time::Duration::from_millis(16));
        }
        host_call("Signal.Fire", &json!({
            "name": "sim.done",
            "args": [{ "handle": handle }],
        }));
    });
    json!({ "started": true })
}

The Luau side can FFI.RegisterSignal("sim.done", sig) once, then connect to sig as it would any other Signal — the engine pumps the fire on the main thread next frame.

Custom object state

The World RPC family is a shared JSON k/v store both sides read and write. Use it when the DLL wants to keep structured per-entity state Luau can introspect (loot tables, AI memory, profiler counters, save snapshots): 

// inside the DLL
host_call("World.Set", &json!({
    "key": format!("npc.{}", id),
    "value": { "hp": 42, "target": "player", "alerted": true },
}));

-- from Luau
local npc = FFI.GetData("npc.7")
if npc.alerted then playAlertSound() end

Cross-platform builds

A cdylib produces the platform-native shared library by default. The engine's loader looks for:

  • Windows: <name>.dll
  • Linux: lib<name>.so then <name>.so
  • macOS: lib<name>.dylib then <name>.dylib

Build separately per target (cargo build --release --target x86_64-pc-windows-msvc, etc.). Drop each artifact into the matching platform's bin/. The Luau code — FFI.Load("name") — stays the same.

Shipping with a package

A package (a folder with ManagedInfo.toml or a pre-built .managed bundle) can include its own bin/ directory. ruzit build merges every package's bin/ into Generated/bin/ so end users get a single tree with every native dependency in place. See Packages → Native side files.

Safety rules

  • Don't dereference the engine's pointers after returning. name and args are only valid for the duration of one ruzit_ffi_call — copy what you need before the function returns.
  • Catch panics at the FFI boundary. A Rust panic that propagates across a extern "C" boundary is UB. Wrap risky bodies in std::panic::catch_unwind if your library is doing anything that could panic on bad input.
  • Free your own allocations. The engine calls your ruzit_ffi_free with whatever you returned from ruzit_ffi_call. Don't free pointers you didn't allocate.
  • The DLL has full process privileges. Treat FFI.Load as you would dlopen: only load libraries you built or trust. Player mods should go through the Packages system (Luau bytecode, sandboxed), not arbitrary native code.

A complete worked example

The Examples/ folder ships a full counter-and-world demo that exercises every flavor of the FFI surface:

  • Examples/rust-ffi-counter/ — a cdylib that holds an internal counter, a particle world, drives a BasePart in a circle, paints a DrawableImg from a worker thread, and fires named signals back into Luau when it's done.
  • Examples/luau-ffi-counter/ — the runnable Ruzit project that loads it.

Build the rust side with cargo build --release, drop the resulting library into Examples/luau-ffi-counter/bin/, and ruzit test from there.
