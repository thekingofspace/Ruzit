Migrating from Roblox

Ruzit's Lua-facing API was modelled on Roblox — BasePart, CFrame, Color3, :Connect, TweenService, PhysicsService. If you've shipped a Roblox game, most of your muscle memory works. This page is the short list of where it doesn't, and how to translate the patterns that change.

Always open a window first

Roblox starts you inside a running DataModel with a camera, a viewport, and a script context already wired up. Ruzit doesn't. Your Main.luau is the entry point of a cold process, so before any rendering, GUI, camera, or input API will do anything, you have to open the window yourself: 

local Window = import("Window")
local win = Window.Open({ Title = "My Game", Width = 1280, Height = 720 })

Calling Renderable.BasePart, GUI.Basic.Square, win:GetViewport(), or anything that touches input or the swapchain before Window.Open will either error or sit silently with no surface to render to. Open the window in line 1-3 of Main.luau and you'll never think about it again.

Only one window per process — calling Window.Open twice throws. Hang onto the returned handle; it's how you get the camera (win:GetViewport()), close the app (win:Close()), and react to resize / focus signals.

The mental-model shift

Three things change. Internalise these and the rest is just spelling.

RobloxRuzit
The engine starts; Workspace, Players, game, and a camera already exist. Scripts attach to instances and run when those instances enter the tree. The engine starts an empty Luau VM and runs your Main.luau top to bottom. There is no game, no Workspace, no DataModel. You import what you need and create what you want. Including the window.
Client / server split. LocalScript, Script, ModuleScript; FilteringEnabled; RemoteEvent. One process. Every .luau file is a module; there is no client/server boundary by default. Use Net if you want networking, and Actor for parallelism. Otherwise it's all the same VM.
You write Lua, Roblox owns the executable. Studio ships the game. You write Luau, you own the executable. ruzit build produces a single cross-platform launcher you hand directly to players or to Steam. See CLI.

Your first day in Ruzit Studio

If you've only ever shipped on Roblox, your tooling instinct is "open Studio". Ruzit doesn't have a Studio. The day-one mapping:

What you used in RobloxWhat replaces it in Ruzit
Roblox Studio (the IDE) Your editor of choice. ruzit init drops a .vscode/settings.json wired up for the Luau LSP, so VS Code with the Luau Language Server extension is the path of least resistance — hover docs, autocomplete, and type errors all just work. JetBrains / Sublime / nvim also work; point them at types.d.luau.
The Explorer panel Your file tree. Every .luau file is a module; folders are folders. There is no separate "Explorer hierarchy" living alongside your scripts.
The Properties panel Code. You don't click a part and edit BrickColor; you write part.Color = Color3.fromRGB(...). Every property is reachable from script and visible via LSP hover.
The Output window The terminal you ran ruzit test in. print() goes to stdout; errors and Lua tracebacks go to stderr in red.
The Toolbox / Marketplace Files on disk. Drop .png / .fbx / .ogg into assets/ and reference them with Asset.GetAsset. No asset IDs, no upload step.
The Play button ruzit test in your terminal. Same effect: it spins up the engine pointing at your project folder. Edit a script, stop the process, run ruzit test again.
Publish to Roblox ruzit build. Produces a Generated/<name>.exe + a Generated/Managed/ folder. Ship the whole folder — that's the game.
Edit-while-running. Roblox Studio lets you tweak a script and see results without restarting. Ruzit doesn't — the engine boots from Main.luau, runs your code, and exits when the window closes. The dev loop is edit, stop, ruzit test again. Most projects boot to a usable state in under a second, so this is faster in practice than it sounds.

Project structure .rbxl place file

Roblox stores everything — scripts, parts, assets, services, settings — inside an opaque .rbxl place file. Ruzit is the opposite: a Ruzit project is a folder of plain text and asset files you can diff, commit, and zip up. ruzit init MyGame scaffolds the skeleton:

Roblox — a place file
  • MyGame.rbxl opaque binary blob
    • ServerScriptService
      • Main Script instance
      • Combat ModuleScript
    • ReplicatedStorage
      • Shared ModuleScripts
    • Workspace
      • Baseplate
      • (your parts)
    • StarterGui
      • HUD ScreenGui
    • Lighting / SoundService / etc.
Ruzit — a project folder
  • MyGame/
    • Main.luau entry point, runs top to bottom
    • build.toml name, version, build flags, icon
    • types.d.luau LSP / autocomplete definitions
    • .luaurc require() path aliases
    • .vscode/settings.json editor wiring
    • assets/
      • ui/logo.png
      • props/crate.fbx
      • sfx/hit.ogg
    • modules/
      • combat.luau require("./modules/combat")
      • hud.luau

Main.luau is the only entry point the engine cares about — everything else is reached from it via require. There is no StarterPlayerScripts or ServerScriptService equivalent; if you want a script to run, require it from Main.luau (directly or transitively).

build.toml plays the role Roblox's Game Settings menu plays: name, version, icon, build flags, Steam app id, etc. See build.toml.

Running commands from your terminal No Play button

Roblox hides the build / run step entirely — you click Play and Studio takes it from there. Ruzit doesn't have a Play button. Every command (ruzit init, ruzit test, ruzit build, …) gets typed into a terminal — a plain text window where you tell the computer what to run. If you've never opened one before, this is the one-time hurdle, and it's smaller than it looks.

Get the ruzit binary on PATH first. Drop ruzit and ruzitrun into a folder that's on your system PATH (Windows: C:\Windows\System32 works in a pinch, or anywhere you've added to PATH; Linux: /usr/local/bin or ~/.local/bin). Without this, typing ruzit in a terminal will say "command not found". Test it: open any terminal, type ruzit, hit Enter — you should see the help text print.
Windows

The slickest way to open a terminal already pointed at your project folder, the trick most Roblox devs haven't seen:

  1. Open File Explorer and browse to the folder that contains your project (the one with Main.luau and build.toml in it).

  2. Click the address bar at the top of File Explorer (the strip that shows the path, e.g. This PC > Documents > MyGame). It turns into an editable text field.

  3. Type cmd (just the three letters — you're replacing the path) and press Enter.

    A black Command Prompt window pops open, already inside your project folder. You'll see something like: 

    C:\Users\you\Documents\MyGame>_

  4. Type the Ruzit command you want and press Enter: 

    C:\Users\you\Documents\MyGame> ruzit test

    The engine boots, the window opens, your game runs. Close the game window (or press Ctrl + C in the Command Prompt) and you're back at the prompt, ready to run it again after edits.

Other ways to open a terminal in a folder on Windows, in case the address-bar trick ever breaks:

  • Right-click in the folder while holding Shift — "Open PowerShell window here" appears in the context menu.
  • Windows Terminal (the modern, tabbed terminal Microsoft ships) — right-click any folder and pick "Open in Terminal" on Windows 11.
  • Press Win + R, type cmd, hit Enter, then cd into your project folder manually: 
    cd C:\Users\you\Documents\MyGame
ruzit test
Linux

Same idea as Windows — open a terminal sitting inside your project folder, then type the command. The exact menu wording depends on your desktop environment.

  1. Open your file manager and browse to the folder containing Main.luau and build.toml.

  2. Right-click an empty area inside the folder and look for one of:

    • GNOME Files / Nautilus — "Open Terminal" (built in on Ubuntu 22.04+ and Fedora 38+; older systems need nautilus-open-terminal / nautilus-extension-gnome-terminal).
    • KDE Dolphin — "Open Terminal Here", or just press F4 in any folder to drop a terminal into the bottom pane.
    • XFCE Thunar — "Open Terminal Here" via the thunar-extras package.
    • elementary Files / Cinnamon Nemo / MATE Caja — "Open in Terminal", present by default on most distros.

  3. A terminal window opens, already cd'd into the project folder. The prompt looks like: 

    you@host:~/projects/MyGame$ _

  4. Type the Ruzit command and press Enter: 

    $ ruzit test

    Close the game window or press Ctrl + C in the terminal to stop, then run it again after edits.

No "Open Terminal Here" entry? Three reliable fallbacks:

  • Press Ctrl + Alt + T to launch a fresh terminal anywhere on GNOME / KDE / XFCE / Cinnamon, then cd into your project: 
    $ cd ~/projects/MyGame
$ ruzit test
  • Launch the terminal binary directly — gnome-terminal, konsole, xfce4-terminal, alacritty, kitty, or whatever your distro ships.
  • On a server with no desktop at all, SSH in and cd normally. ruzit test needs a display server (X11 / Wayland) to open the window, but ruzit build works headless — you can package a release on a headless build box.
Make the binary executable. Linux files don't get an "executable" bit by default when downloaded. If ruzit errors with "Permission denied" or "bash: ruzit: command not found" after you've placed it on PATH, mark it executable once: 
$ chmod +x ~/.local/bin/ruzit ~/.local/bin/ruzitrun
~/.local/bin is on most distros' default PATH and doesn't need sudo. Use /usr/local/bin (with sudo) if you want the binary available to every user on the system.
If ruzit isn't recognised. "command not found" / "'ruzit' is not recognized as an internal or external command" means the binary isn't on your PATH. Either move it onto PATH (recommended) or run it by full path, e.g. C:\Tools\ruzit.exe test on Windows or ./ruzit test from the folder containing the binary on Linux.

Running and shipping F5 / File → Publish

The whole CLI workflow is eight verbs. The two you'll touch every day are ruzit test (the Play button) and ruzit build (the Publish button). They are both run from your terminal at the project root.

Roblox actionRuzit commandWhat it does
File → New Place ruzit init MyGame Scaffold a new project folder with Main.luau, build.toml, assets/, and a fresh types.d.luau.
Play button (F5) ruzit test Boot the engine pointed at your project. No packaging, no encryption — edits hit the next run.
File → Publish to Roblox ruzit build Produces Generated/<name>.exe + a Managed/ folder. Ship the whole Generated/ directly to players or to Steam.
(no equivalent) ruzit initpackage MyDLC Scaffold a DLC / mod package that drops next to a project and ships as a separate, encrypted .managed bundle. See Packages & DLC.
(no equivalent) ruzit refresh-types Re-download types.d.luau so your autocomplete tracks the engine version you're actually running.
You own the executable. The output of ruzit build is yours — no marketplace, no platform gate, no revenue cut. Distribute it however you want: direct download, itch.io, Steam, GOG. The engine binary is GPL-friendly and the launcher is just a regular signed-able Win32 / ELF executable.

Hello, cube Workspace + Camera

The minimum viable "show something" program in each engine. The Roblox version assumes a baseplate; the Ruzit version is the whole program, including the window.

Roblox — Script in ServerScriptService
local part = Instance.new("Part")
part.Size     = Vector3.new(2, 2, 2)
part.Position = Vector3.new(0, 5, 0)
part.Anchored = true
part.Parent   = workspace
Ruzit — Main.luau
local Window     = import("Window")
local Renderable = import("Renderable")
local Vector     = import("Primitives").Vector

local win  = Window.Open({ Title = "Hello", Width = 1280, Height = 720 })
local part = Renderable.BasePart("Cube")
part.Size  = Vector.new(2, 2, 2)
part.CFrame = Primitives.CFrame.new(Vector.new(0, 5, 0))

Notice three things: Instance.new("Part") becomes Renderable.BasePart("Cube") — there's no instance tree, parts exist standalone the moment they're created. Vector3 is just Vector. And the position setter is gone — parts have a CFrame, not a separate .Position field (you read part.CFrame.Position).

Math primitives Vector3, CFrame, Color3

Roblox
Vector3.new(1, 2, 3)
CFrame.new(0, 5, 0)
Color3.fromRGB(255, 80, 80)
UDim2.new(0, 200, 0, 12)
Ruzit
local P = import("Primitives")

P.Vector.new(1, 2, 3)
P.CFrame.new(P.Vector.new(0, 5, 0))
P.Color3.fromRGB(255, 80, 80)
P.Dim.new(200, 12)  -- pixels only, no scale axis

Dim replaces UDim2 and is pixel-only by default — Ruzit's GUI primitives don't have Roblox's scale / offset duality. If you want a fraction-of-window layout, read win:Width() / win:Height() and do the math yourself; signals on the window handle make this trivial.

A non-obvious bonus: every Ruzit API that takes a Vector also accepts a raw Luau vector(x, y, z) primitive. So part.Size = vector(1, 2, 3) is valid, and faster in hot loops because the read never crosses the FFI boundary. See Primitives.

Parts and the scene graph Instance / Parent / workspace

Roblox
local part = Instance.new("Part")
part.Shape    = Enum.PartType.Ball
part.Size     = Vector3.new(2, 2, 2)
part.Color    = Color3.fromRGB(90, 200, 120)
part.Anchored = true
part.Parent   = workspace

-- ChildAdded fires on every Instance
workspace.ChildAdded:Connect(function(c) print(c) end)
Ruzit
local part  = Renderable.BasePart("Sphere")
part.Size  = Vector.new(2, 2, 2)
part.Color = Color3.fromRGB(90, 200, 120)
-- no Parent. The part exists. The renderer sees it.
-- no Anchored. Anchored is the default; opt into physics
-- by passing the part to PhysicsService.

-- need to group / move / clone parts together?
local Objects = import("Objects")
local rack    = Objects.Movable()
rack:AddChild(part)
Key difference

There is no instance tree. Parts are not children of anything; creating one registers it with the renderer, and that's it. If you need parenting semantics — move-the-parent-and-children-follow, clone-a-whole-rig — use Objects' Movable / Sizable / ClonableContainer composers. They give you Roblox's "model" behaviour without bringing back the whole DataModel.

Modules and require ModuleScript / require()

If you're familiar with using Rojo, this will feel very similar. Ruzit projects are folders of .luau files on disk, edited in an external editor (VS Code is the path of least resistance), with require resolved by file path. If you've ever set up a Rojo project mapping src/ into ReplicatedStorage, the mental model here is the same one — just without the sync step, because the files are the project. No default.project.json, no rojo daemon, no Studio round-trip. You point ruzit test at the folder and it runs.

A module in Ruzit is any .luau file that ends in return <something>. Same convention as Roblox's ModuleScript. The difference is that you reach modules by file path instead of by walking the instance tree.

Roblox — ModuleScript by instance path
-- ServerScriptService/Combat.lua (ModuleScript)
local Combat = {}
function Combat.deal_damage(t, n) ... end
return Combat

-- elsewhere:
local Combat = require(
    game:GetService("ServerScriptService").Combat)
local Shared = require(
    game:GetService("ReplicatedStorage").Shared)
Ruzit — ModuleScript by file path
-- modules/combat.luau
local Combat = {}
function Combat.deal_damage(t, n) ... end
return Combat

-- elsewhere, e.g. Main.luau:
local Combat = require("./modules/combat")
local Shared = require("./modules/shared")

The three forms of require

Three path styles, in order from "everyday" to "rare":

FormResolves to
require("./foo/bar") Relative to the directory of the current .luau file (the same one __dirname reports). Drop the .luau extension — the loader adds it. This is what you'll use 95% of the time.
require("@Game/modules/foo") Project-root-anchored. The @Game alias is installed automatically by ruzit scaffold / ruzit init and points at ./. Use it when a deeply nested module needs to reach back up to a sibling without counting ../../../.
require("@PkgId") / require("@PkgId/sub") Cross-package — pulls from a sibling Managed/ package (a DLC, a mod, or just a shared library you've packaged separately). Aliases are regenerated by ruzit scaffold by walking the project for ManagedInfo.toml files.

The .luaurc file

Ruzit's .luaurc is Luau's standard config file (the same one Roblox / Rojo use), shaped here to power @ aliases. ruzit init generates a starter for you; ruzit scaffold regenerates it any time you add or remove a packaged sibling. Typical contents after running ruzit init MyGame: 

{
    "languageMode": "strict",
    "aliases": {
        "Game": "./"
    }
}

After dropping a DLC folder (with its own ManagedInfo.toml) next to Main.luau and running ruzit scaffold, the same file becomes: 

{
    "languageMode": "strict",
    "aliases": {
        "Game": "./",
        "CoolDLC": "./CoolDLC"
    }
}

From any script in the project you can now write require("@CoolDLC/init") and the LSP will autocomplete against it. The DLC's own init.luau is whatever it chooses to expose; same module convention as everywhere else.

And a representative Main.luau that wires it together: 

-- Main.luau
local Window  = import("Window")
local Process = import("Process")

local win = Window.Open({ Title = "My Game", Width = 1280, Height = 720 })

local Player = require("./modules/player")
local HUD    = require("./modules/hud")
local Level  = require("./scenes/level_01")

local player = Player.new(win)
Level.load(player)
HUD.attach(player)

Process.Heartbeat:Connect(function(dt)
    player:Update(dt)
end)

VS Code is the path of least resistance

Ruzit doesn't ship its own IDE. The recommended setup is Visual Studio Code with the Luau Language Server extension. ruzit init writes a .vscode/settings.json alongside your project so the extension knows where to look the moment you open the folder — you don't have to configure anything by hand. You get:

  • Autocomplete for every import("X") return value — the LSP follows the type through to types.d.luau and surfaces every property, method, and signal with the right type signature.
  • Hover docs. Mouse over :Connect / Vector.new / part.CFrame and see the same prose that's on these doc pages.
  • Inline type errors. Mistype a property name or pass the wrong arg type and the editor red-squiggles it before you ever hit ruzit test.
  • Go-to-definition for your own modules. Cmd / Ctrl + click a require'd symbol to jump straight to its definition.
  • Refactor-rename for locals and module exports.

Other editors work too — the Luau LSP is editor-agnostic (JetBrains, nvim, Sublime, Helix all have integrations). If your autocomplete ever falls out of date with the running engine, run ruzit refresh-types to pull a fresh types.d.luau and the LSP will pick it up on next save.

Events RBXScriptSignal :Connect

Identical surface. :Connect, :Once, and :Wait all exist. The only difference is that you can build your own typed signals from script via Signal.new() — in Roblox you'd reach for BindableEvent.

Roblox
local ev = Instance.new("BindableEvent")
ev.Event:Connect(function(dmg) print(dmg) end)
ev:Fire(25)
Ruzit
local Signal = import("Signal")
local hit    = Signal.new()
hit:Connect(function(dmg) print(dmg) end)
hit:Fire(25)

Per-frame loops RunService.Heartbeat

RunService is gone — its two useful signals (Heartbeat and RenderStepped) live on Process now. Same shape, same dt-in-seconds payload.

Roblox
local RunService = game:GetService("RunService")

RunService.Heartbeat:Connect(function(dt)
    player:Update(dt)
end)

RunService.RenderStepped:Connect(function(dt)
    camera:Follow(player, dt)
end)
Ruzit
local Process = import("Process")

Process.Heartbeat:Connect(function(dt)
    player:Update(dt)
end)

Process.RenderStepped:Connect(function(dt)
    camera:Follow(player, dt)
end)

Camera Workspace.CurrentCamera

Roblox gives you workspace.CurrentCamera automatically; in Ruzit the camera belongs to the window you opened, so you ask the window for it. There's one camera per window and it's a true singleton — every call returns the same object.

Roblox — LocalScript
local cam = workspace.CurrentCamera
cam.CameraType    = Enum.CameraType.Scriptable
cam.CFrame        = CFrame.new(0, 5, 10)
cam.FieldOfView   = 75
Ruzit
local cam = win:GetViewport()
cam.CFrame = CFrame.new(Vector.new(0, 5, 10))
cam.FOV    = 75

-- third-person follow with offset, no Heartbeat loop needed:
cam:LinkTo(player, CFrame.new(Vector.new(0, 1.5, -6)))

Ruzit's cam:LinkTo(target, offset, callback) replaces the per-frame "set cam.CFrame from RenderStepped" dance most Roblox third-person cameras do. The engine evaluates the link after physics ticks each frame, so the camera never lags one frame behind its target.

Input devices UserInputService

Roblox funnels keyboard, mouse, gamepad, and touch through one UserInputService with a tagged UserInputType. Ruzit splits them into one library per device kind — Mouse, Keyboard, Gamepad. Each is a flat library with its own signals and snapshot queries. There's no "input began / changed / ended" enum to switch on — the device dictates which library to import.

Roblox
local UIS = game:GetService("UserInputService")

UIS.InputBegan:Connect(function(input, processed)
    if processed then return end
    if input.KeyCode == Enum.KeyCode.Space then
        player:Jump()
    end
end)

UIS.InputChanged:Connect(function(input)
    if input.UserInputType == Enum.UserInputType.MouseMovement then
        aim:RotateBy(input.Delta.X, input.Delta.Y)
    end
end)
Ruzit
local Keyboard = import("Keyboard")
local Mouse    = import("Mouse")

local space = Keyboard:GetKeyId("Space")

Keyboard.InputChanged:Connect(function(id, name, state)
    if id == space and state == "Begin" then
        player:Jump()
    end
end)

Mouse.Moved:Connect(function(pos, delta)
    aim:RotateBy(delta.X, delta.Y)
end)

A few pattern shifts to internalize:

  • Polling is free. Keyboard:IsKeyDown("w") and Mouse.Position are cheap snapshot reads — do them inside Process.Heartbeat instead of tracking every key with begin/end events. (Roblox makes you do the same with UserInputService:IsKeyDown, but in Ruzit it's the recommended style.)
  • Mouse lock is one line. Mouse.Locked = true; Mouse.Visible = false — no MouseBehavior enum, no Studio-only caveats.
  • Mouse buttons fire through Mouse.InputReceived. Payload is ("MouseButton1" / "MouseButton2" / ..., "Begin" / "End") — the same shape as Keyboard.InputChanged.
  • No gameProcessedEvent flag. The engine doesn't consume input on your behalf, so there's nothing to gate against. If you want a "GUI eats the click" pattern, write it yourself.

GUI ScreenGui / Frame / TextLabel

Roblox builds GUI by parenting Instances under a ScreenGui. Ruzit gives you flat primitive factories: GUI.Basic.Square, Circle, Triangle, Image, Font. Each returns a free-standing primitive you position in screen-space pixels.

Roblox
local gui  = Instance.new("ScreenGui")
gui.Parent = game:GetService("Players").LocalPlayer.PlayerGui

local bar  = Instance.new("Frame", gui)
bar.Size            = UDim2.new(0, 200, 0, 12)
bar.Position        = UDim2.new(0, 24, 0, 24)
bar.BackgroundColor3 = Color3.fromRGB(155, 209, 59)
Ruzit
local GUI = import("GUI")
local Dim = import("Primitives").Dim

local bar = GUI.Basic.Square()
bar.Size     = Dim.new(200, 12)
bar.Position = Dim.new(24, 24)
bar.Color    = Color3.fromHex("#9bd13b")

GUI primitives always render on top of the 3D scene; you do not parent them anywhere. If you want a Frame-style group container, drop the primitives into an Objects.Movable() and move that — same idea, different name.

TweenService TweenService:Create

The closest mapping in this whole guide. The constructor shape is different (positional args instead of a TweenInfo table) but every easing style / direction string is the same, and the :Play() / Completed dance is identical.

Roblox
local TS = game:GetService("TweenService")
local info = TweenInfo.new(1.5,
    Enum.EasingStyle.Bounce,
    Enum.EasingDirection.Out)

local tw = TS:Create(part, info, {
    CFrame = CFrame.new(0, 10, 0),
    Color  = Color3.fromRGB(255, 80, 80),
})
tw:Play()
tw.Completed:Connect(function() print("done") end)
Ruzit
local TweenService = import("TweenService")

local tw = TweenService.new(part, 1.5, "Bounce", "Out", {
    CFrame = CFrame.new(Vector.new(0, 10, 0)),
    Color  = Color3.fromRGB(255, 80, 80),
})
tw:Play()
tw.Completed:Connect(function() print("done") end)

Physics Anchored = false

Roblox sims everything by default; you opt out per part with Anchored = true. Ruzit is the opposite: parts are static until you hand them to a PhysicsService plane, which then owns the part's CFrame each frame. Multiple planes can coexist (main world, debris, puzzle layer) and they don't interact.

Roblox
local ball = Instance.new("Part", workspace)
ball.Shape    = Enum.PartType.Ball
ball.Anchored = false      -- opt in to physics
ball.Position = Vector3.new(0, 10, 0)

-- impulses via :ApplyImpulse on the Part itself
ball:ApplyImpulse(Vector3.new(0, 0, 12) * ball.AssemblyMass)
Ruzit
local PhysicsService = import("PhysicsService")

local world = PhysicsService.New({
    Gravity = Vector.new(0, -50, 0),
    Threads = 4,
})

local ball = Renderable.BasePart("Sphere")
ball.CFrame = CFrame.new(Vector.new(0, 10, 0))

local body = world:Add(ball)        -- opt in
body.Bounciness = 0.7
body:ApplyImpulse(Vector.new(0, 0, 12))

The body wrapper is where the physics-specific knobs live (Bounciness, HitBoxQuality, Velocity, ApplyImpulse). The underlying BasePart's .CFrame still reads — you just don't write to it while the body is owned by a plane (the plane will overwrite next tick).

Audio Sound Instance

Roblox's Sound object is a Instance you parent and :Play(). Ruzit's SoundByte is a flat library with the same playback verbs — :Play, :Stop, :Pause, .Volume, .PlaybackSpeed — but tracks are loaded once from a SoundAsset and can be cheaply re-triggered.

Roblox
local snd = Instance.new("Sound")
snd.SoundId = "rbxassetid://12345"
snd.Volume  = 0.5
snd.Parent  = workspace
snd:Play()
Ruzit
local SoundByte = import("SoundByte")
local Asset     = import("Asset")

local clip = Asset.GetAsset("Sound", "sfx.hit")
local snd  = SoundByte.new(clip)
snd.Volume = 0.5
snd:Play()

Loading assets rbxassetid://

Roblox assets live on Roblox's CDN, identified by numeric IDs that you upload via the website or Studio. Ruzit assets live in your project's assets/ folder — they're just files on disk that ship inside the launcher.

Roblox
-- Upload the .png in Studio, copy the asset id, then:
local img = Instance.new("ImageLabel", gui)
img.Image = "rbxassetid://1234567890"

local snd = Instance.new("Sound", workspace)
snd.SoundId = "rbxassetid://9876543210"
Ruzit
-- Drop the file at assets/ui/logo.png, then:
local Asset = import("Asset")

local logo = Asset.GetAsset("Image", "ui.logo")
local hit  = Asset.GetAsset("Sound", "sfx.hit")
local crate = Asset.GetAsset("Model", "props.crate")

The dotted path is folder-relative: "ui.logo" resolves to assets/ui/logo.<ext>, with the loader probing the extensions valid for the asset kind. The first argument ("Image" / "Sound" / "Model" / "Font" / "Shader" / "File") picks the loader.

A few practical upgrades over Roblox:

  • No upload step. Edit the .png, re-run ruzit test, the new pixels are there. No moderation queue, no asset id update.
  • Real file formats. Images are .png / .jpg / .webp; sounds are .ogg / .mp3 / .wav; models are .fbx or .obj. No Roblox-specific intermediate format.
  • Loading from outside the bundle. If you want to load from the user's filesystem at runtime (mod support, user content), use Asset.ImportAsset instead of GetAsset. See Asset.
  • Caching is automatic. Asset.GetAsset caches by path, so a second call with the same path returns the same handle — no bookkeeping required.

Cleanup and Destroy Parent = nil / :Destroy()

Roblox's GC is "remove from the tree". Set part.Parent = nil or call :Destroy() and eventually the engine collects it. Ruzit has no tree, so removal is explicit: every userdata with engine-owned resources (BaseParts, EffectVolumes, SoundBytes, GUI primitives, physics bodies, tweens, etc.) exposes a :Destroy() method that releases its GPU / audio / physics resources and unhooks it from the renderer. After :Destroy() the userdata still exists as a Lua value — it just no longer does anything.

Roblox
part.Parent = nil          -- detach, GC eventually
part:Destroy()              -- detach + tag for cleanup
Ruzit
part:Destroy()              -- free GPU buffers + remove from scene
-- the local 'part' var still references dead userdata.
-- assign nil if you want it collected by the Lua GC.
part = nil
Don't rely on Lua GC to clean up engine resources. Roblox parts get cleaned up by the engine even if you forget to call :Destroy() (eventually). Ruzit doesn't — if you drop the last reference to a BasePart without destroying it, the GPU mesh and physics body leak for the rest of the process. Call :Destroy() when you're done. Signals also have connection:Disconnect() — remember to disconnect if your handler holds references that should be freed.

Gotchas that bite Roblox devs

Things that don't exist that you might reflexively type.
  • workspace, game, script.Parent — no global instance tree.
  • part.Parent = workspace — creating a part already registers it with the renderer.
  • part.Position as a setter — position lives on part.CFrame.Position; write the full CFrame back to move a part.
  • Anchored = true — anchored is the default; you opt in to physics, not out of it.
  • Enum.* — most enums are plain strings in Ruzit (e.g. "Bounce", "Out", "Sphere").
  • Instance:GetChildren() — if you need parenting, use Objects containers, which expose :GetChildren() on the container itself.
And one thing Ruzit gives you that Roblox doesn't. You own the launcher. ruzit build spits out an .exe (or ELF binary on Linux) that runs your scripts unmodified, ready to ship straight to players or to Steam. No marketplace, no studio, no DataModel boot — just your Main.luau, opening a window.

FAQ — the things every Roblox dev asks on day one

Nothing's rendering. What gives?

You forgot Window.Open. The first three lines of every project are import("Window"), Window.Open({...}), and holding the returned handle. Without it, parts and GUI primitives have nowhere to draw, and inputs have no surface to come from. See the banner at the top of this page.

Where does print() go?

The terminal you ran ruzit test in. Errors and Lua tracebacks go to stderr in red. If you're running a packaged build, attach a console with the exe-windowed = false setting in build.toml, or pipe the launcher's output to a file.

Where do I put my game code? Is there a "ServerScriptService" folder?

Main.luau is the entry point. Anything else you want to run, require it from Main.luau directly or transitively. There is no special folder — the engine doesn't auto-load anything outside Main.luau. Organise modules however you like; most projects end up with a modules/ or src/ directory.

Can I open a .rbxm / .rbxl file?

No. Roblox's place / model format is proprietary and tightly coupled to the DataModel. Export geometry to .fbx or .obj and load it with Asset.GetAsset("Model", ...). Blender can re-export anything you've got in Studio.

Is there hot reload like Studio's "Edit Mode"?

Not yet. The dev loop is edit, stop, ruzit test. Most projects boot in under a second, so the round-trip is fast in practice. If you want live tweak-and-see for a specific value, expose it on a debug GUI and rebind a key with Keyboard.InputChanged.

Where's LocalPlayer / Players.LocalPlayer?

There is no Players service because there's no platform handling player identity. Ruzit is a single-process engine, so "the player" is whichever piece of code you wrote to represent them — usually a table or class you hand a BasePart and a Controller. If you want multiplayer, see Net and Steam (lobbies, P2P).

Why does Luau autocomplete look slightly different?

Because it's coming from your project's types.d.luau rather than from Roblox's API dumps. That file is the source of truth for every import("X") return type, every property, every signal payload. Run ruzit refresh-types if you update the engine and want autocomplete to track the new version.

How do I see FPS, draw calls, memory usage?

import("Debug"). It exposes frame timings, renderer counters, GPU memory, and Lua memory in a single snapshot object. Drop it onto a GUI.Basic.Font readout or print it from Process.Heartbeat — whichever you prefer.

Can I script in Lua instead of Luau?

Files run through Luau, the same dialect Roblox uses. Plain Lua 5.1 / 5.2 / 5.3 scripts will mostly work too — Luau is a superset. Types, generalised iteration, and the continue keyword are bonuses you can ignore.

Is there a Studio-like scene editor?

No first-party one. Authoring is code-first by design — scenes are built procedurally in Luau or imported from .fbx. If you want a level-editor feel, build one inside your game: ruzit test a tool mode that lets you place parts with the mouse, dump the result to a file via IO + Serde, then load it on game-mode start. Plenty of projects ship this way.

Where to next? Start with Window (the line of code you'll write first in every project), then Primitives, then Renderable. After that, the sidebar is your map.
